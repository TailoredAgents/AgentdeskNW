# AI employee contracts and catalog

All 16 proposed specialists share the registry in `src/server/registry.ts` and the browser/server `Specialist` contract. Catalog presence means architecture coverage; it does not prove execution capability. Runtime status is authoritative: `demo` means operational against fictional/local data, `ready` means an implemented capability within its stated boundary, and `planned` means no executable specialist yet.

In opt-in `admitted_demo` text execution, the master can now request a separate focused assessment through `consult_specialist`. The selected specialist receives its current role-permitted operating method, employee preferences/request and selected current tool receipts. It returns structured observations, assumptions, gaps and recommended next steps for the master to use. It has no tools of its own; execution still uses the existing scoped business services and required employee decisions. Each assessment consumes the original request's bounded allowance, including its $1 approval rule and pause/cancel/recovery controls. Web, native text/dictation and linked employee SMS/Slack use that shared path. This does not change registry readiness, establish sixteen independently trained agents or prove superior judgment. See [the execution contract](WORK_EXECUTION.md#focused-paid-specialist-assessments) and the existing model-quality evaluation gates.

## Common contract

A definition includes unique ID, name, purpose, category, allowed roles, input/context requirements, supported tool names, output descriptions and approval policy. Execution receives a trusted `Actor` and validated inputs; returns `ToolResult` containing specialist IDs, user-safe message, structured data and actual artifact references. Usage/audit records attach actor, tenant, office, operation, timestamp and outcome outside the model’s response.

The contract permits reuse across tenants. Names and tenant terminology must not become hard-coded customer authorization assumptions. All specialists inherit record scoping, source provenance, secret handling and prompt-injection controls.

## Coordination rules

Copilot owns conversation and selects tools. Tool schemas expose no tenant/role override and no generic arbitrary CRM mutation. A specialist cannot expand its permissions by requesting another specialist. Composite work returns linked artifacts: for example research job → duplicate results → reviewable import. The orchestrator must retrieve completed results before describing a job as finished.

Direct catalog navigation may open an implemented workflow or explain what is missing. Planned specialists must not produce a fake completion animation. When a permitted read-only tool covers only part of a specialist’s purpose, describe that limit explicitly.

### Repeatable model-quality evaluation

The generic-versus-specialist comparison remains unrun for all 35; null scores mean missing evidence, not a zero-quality result.

`npm run test:specialist-quality` reports pending coverage for each role and all sixteen specialists. `-- --export /tmp/specialist-cases.json` exports the reviewer pack; `-- --review /path/to/reviews.json` accepts either a review array or the exported pack with its `reviews` populated. `-- --prepare /tmp/new-specialist-sample` writes six randomized two-turn advisory model packets for the three new cases, separate blinded-review templates and a separate arm key. Use a new directory and `--sample 2` for a repeat. Feed each turn separately and save the first answer before revealing the correction. Model payloads omit expected answers and runtime teaching examples; do not send the entire reviewer pack or arm key to the model/reviewer respectively. These offline benchmark commands do not call a provider, spend credits, run application tools or grade responses.

Paired means require recorded identical model, application revision, run, facts/request, tools, model configuration and whole-task budget; only the specialist instructions differ. Missing or unequal metadata excludes the pair with a visible reason. These declarations are not independently verified provider receipts: retain raw inputs/outputs and usage separately. Legacy reviews remain inspectable, and fixtures never enter means. Advisory samples do not establish actual tool execution or company acceptance.

Review records now declare reviewer provenance: human, model (with the recorded model label), or unspecified for legacy records. Blinding is a recorded procedure, not independently verified proof.
